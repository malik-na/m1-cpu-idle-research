# Prospective PCPU/PCPM PS3 signal screen for issue #6

Status: **design only**. No new register read, module load, kernel build, or reboot is authorized by this document. This is a new falsifiable screen after the [first native PCPM packet](native-evidence/mmio-abi2/README.md): 90 successful reads of PMGR `PCPM` at `+0x48` were all `0x000021f0` (`ACTUAL=15`, `DESIRED=0`), including 24 guarded all-P-released samples. Its declared active-versus-released contrast failed. Repeating that sparse `+0x48` run alone would not resolve [issue #6](https://github.com/malik-na/m1-cpu-idle-research/issues/6).

## Candidate and falsifier

The saved [T8103 ADT device map](../../notes/raw/pmgr-device-map.json) places `PCPU0`–`PCPU3` at PS3 indices 4–7 and `PCPM` at index 9. The [pinned m1n1 decoder](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hw/pmgr.py#L4-L42) assigns all ten PS3 slots the same 32-bit `R_PSTATE` layout: `ACTUAL` bits 7:4, `DESIRED` bits 3:0. The [pinned T8103 Linux DT](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8103.dtsi#L1049-L1054) locates the main PMGR bank at `0x23b700000`; reconfirm it on the actual boot. Only these five slots are in this screen:

| Main PMGR offset | Saved ADT name | Physical address on the captured T8103 mapping |
| --- | --- | --- |
| `+0x20`, `+0x28`, `+0x30`, `+0x38` | `PCPU0`–`PCPU3` | `0x23b700020`–`0x23b700038` |
| `+0x48` | `PCPM` | `0x23b700048` |

**PMGR `PCPU3 +0x38` is unrelated to the APSC cluster-resource `LAST_CHG_TIME +0x38` candidate.** They have different bases and access qualifications. This protocol neither reads nor infers anything from APSC `LAST_CHG_TIME`.

Hypothesis: at least one PCPU `ACTUAL` code distinguishes controlled P-core activity from settled software `CPU PD`, returning toward its active reference on wake; PCPM may or may not distinguish all-P release. The counterexample is five constant raw words, read errors/stalls, values that fail to track the individually active core, or a contrast that disappears under observer controls. Only a separately confirmed per-PCPU transition could support a **PMGR-reported per-core state discriminator**. The generic Linux PMGR driver's `0xf` active, `0x4` clock-gated and `0x0` power-gated labels are [used for its managed power domains](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L20-L36); the [T8103 PMGR child nodes](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8103-pmgr.dtsi) start at `+0x100` and do not establish CPU-slot rail semantics. Keep all other bits, including `WAS_PWRGATED`/`WAS_CLKGATED`, in each raw word; their latch/clear semantics are uncalibrated.

## Before any acquisition

1. In a read-only root preflight, pin the *running* J313/T8103 kernel release, Build-ID, config/source/DT/firmware identities, eight-CPU E/P topology, cpuidle state and policy, and main PMGR resource size and `reg-io-width=4`. Verify stock fallback and previously working boot artifacts against their receipts; their presence cannot guarantee a future successful boot. Confirm the current capture instruments' used/unused status. Abort on identity, topology, mapping or ownership mismatch; do not substitute the separate PMGR mini bank.
2. Qualify a 32-bit accessor to the **already existing, internal, clockless main-PMGR syscon regmap**. Do not map `/dev/mem`, construct a competing `ioremap`/cacheable map, bind a new PMGR device, enable a clock, or write a power-state target. The current [built-in PCPM sampler patch](0001-t8103-pcpm-sampler.patch) reads only `+0x48`. Its `syscon_node_to_existing_clockless_regmap()` guard is **not exported** to loadable modules; exported `syscon_node_to_regmap()` may create a mapping and is not an equivalent no-new-map proof. No safe same-boot module path is established. A reviewed built-in extension with a new, verified #6 image, or a separately proven existing-map interface, is required before PCPU reads. This is a #6 preparation gate, not grounds for another #5 reboot.
3. Keep all reads on a verified E-core worker with preallocated records. Predeclare the exact fixed offsets, read order, cadence, phase schedule and maximum attempts; first run a no-MMIO scheduling/records qualification. Before exposing PCPU slots while P cores are released, make an **active-P-only access pilot capped at two five-register rows (ten 32-bit attempts)** and review every raw value, errno, read bracket and machine log. Access to PCPM does not establish PCPU-slot safety during idle. A later five-register MMIO variability pilot is capped at **three fully guarded rows per phase, twelve rows total and sixty 32-bit read attempts**, with no catch-up reads. It cannot by itself calibrate slot identity or physical state. Abort further reads on an error, excessive completed bracket, CPU migration, dropped row or changed topology/power source. A stalled MMIO access may never return to execute that abort; retain recovery and fallback arrangements. Preserve a failed packet; do not automatically repeat it at a faster cadence.

The built-in probe is one-shot per boot. The first fresh #6 boot of a reviewed, two-row-capped image must run `records 2 800 0` with all four P workers active and verify ten timestamp-only word records, zero register-read attempts, map/counter qualification and unchanged machine health. A dry-run plan or synthetic test does not meet this gate. Only after that packet is reviewed may a **second fresh #6 boot of the same linked image** run `mmio 2 800 0`; its source-enforced cap must remain two rows, regardless of the userspace request. Check each P core's software `CPU PD` usage counter immediately before and after the active-only control as an additional no-entry screen, while retaining the raw counter values and treating them as software evidence. The later twelve-row variability screen would need its own reviewed cap change, linked image and fresh-boot gates.

## Controls and evidence packet

Use ordinary unprivileged P workers pinned to the verified four P logical CPUs and an E-core coordinator. Declare multi-second phases before acquisition: all four continuously active; exactly one named P core active with three workers released; all four released; all four active again. Preserve the one-active identity, actual phase boundaries and completed work. Qualify released phases with independent, loss-accounted software-idle entry/exit records; a worker being blocked is not proof its CPU entered `CPU PD`. Exclude all register brackets touching a phase guard and retain the exclusions. Do not import the earlier unverified 240-tick cross-CPU bound as a fact. Without a qualified cross-CPU clock bound or shared ordering stream, a register read is associated with a **coarse workload phase**, not proven inside every core's `CPU PD` interval. No CPU hotplug, direct PMGR writes, forced cluster-off, or idle-policy changes serve as a positive control.

Each retained row must include sequence, scheduled and actual times, reader CPU, phase and its active-core identity, and **five full 32-bit raw words, each with its own before/after timestamp or ordered-counter bracket, read errno and validity bit**. Five serial reads are not an atomic snapshot. Retain row/slot/reader migration and counter errors, skipped/missed slots, recorder overflow, start/stop status, and a private source-to-boot identity packet; publish only a sanitized, hash-linked export with a replayable decoder. Decode `ACTUAL`/`DESIRED` only after preserving raw values. The twelve-row pilot can show access and candidate variability; one isolated edge, one active-core identity or a PCPM `DESIRED` change cannot validate the PCPU name-to-core association.

If that pilot yields a candidate PCPU contrast, write a **separate confirmation protocol before more hardware reads**. Rotate exactly one active worker through each of the four verified P-core identities, with balanced guarded repeated rows per identity, all-active/all-released/wake references, matched no-MMIO and no-collector blocks, and reversed or randomized order where feasible. Specify repetition, exclusion and decision thresholds in advance. To claim a code changed while a named core was in software `CPU PD`, also qualify an independent per-core interval-to-read ordering method, such as a reviewed shared ticket stream or measured capture-wide cross-CPU counter bound; do not infer this from phase labels. Confirm recovery on wake and preserve negative cores/rows. Even this comparison would calibrate only the PMGR-reported code under those conditions.

Compare a matched no-collector workload, an E-core timestamp/record-only run, and the bounded five-register run with the same P workload, power source, brightness, USB/network state, policy, thermal trend and delivered work. Compare software `CPU PD` opportunity, wake behavior, sampler latency and losses. Reverse order or vary cadence only under a new declared protocol if a usable signal emerges. A known Linux-managed PMGR child whose `ACTUAL` follows a natural driver power transition can check the accessor/decoder separately, but it cannot prove PCPM or PCPU sensitivity. Any observed sampler-dependent idle change leaves the state distribution observer-sensitive.

If PCPU codes change while PCPM remains `ACTUAL=15` in the pilot, report a **candidate PCPU phase contrast**, with PCPM still nondiscriminating under those conditions; do not claim core identity or `CPU PD` association until the separate confirmation gates pass. If all five stay constant, report a negative screen for these slots and conditions; possible explanations include genuinely active domains, inaccessible depth, sampling perturbation or status fields insensitive to returning deep WFI. Neither outcome by itself proves full core/cluster rail-off, residency, energy saving, exact transition timing, or a reason to add an APSC wait. An independently qualified whole-system energy/wake measurement may assess consequences, but battery SMC readings are not CPU-rail state measurements.

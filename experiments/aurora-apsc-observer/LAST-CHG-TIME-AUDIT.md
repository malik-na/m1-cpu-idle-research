# T8103 `LAST_CHG_TIME` cannot yet bridge the WFI sample

This is a static source audit for [issue #5](https://github.com/malik-na/m1-cpu-idle-research/issues/5), not a native read of the timestamp register. The [ABI 2 capture](WFI-E-RESULT.md) has four APSC BUSY reads at the first-attempt pre-DSB probe, while the [linked instruction audit](WFI-INSTRUCTION-BOUNDARY.md) places 13 instructions between that read and WFI. Establishing BUSY **at the WFI instruction** requires a timing or continuity bridge that those packets do not contain.

The exact Aurora cpufreq source [defines `APPLE_DVFS_LAST_CHG_TIME` as offset `0x38`](https://github.com/iconidentify/aurora-linux/blob/90a95335a49aec3a0045a76da140452ad6585eb3/drivers/cpufreq/apple-soc-cpufreq.c#L25-L36), with only the comment “Same timebase as CPU counter (24MHz).” In the reviewed tree, that definition is its sole occurrence: the driver does not read it. The [T8103 device tree](https://github.com/iconidentify/aurora-linux/blob/90a95335a49aec3a0045a76da140452ad6585eb3/arch/arm64/boot/dts/apple/t8103.dtsi#L554-L563) gives E/P controller resource bases `0x210e20000` and `0x211e20000`; `+0x38` would be `0x210e20038` and `0x211e20038`. The APSC command is at resource `+0x20`, so the timestamp candidate is command-address `+0x18`. The pinned [Asahi source](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L25-L36) has the same unused definition. Pinned [m1n1 cpufreq code](https://github.com/AsahiLinux/m1n1/blob/ce2b8a43cea4220b602af1005dc9dbfc59c9624e/src/cpufreq.c#L79-L123) polls command BUSY after its own SET but does not use `LAST_CHG_TIME`.

No reviewed source specifies the register's T8103 width, update edge, clock epoch, wrap rule, read side effects, or whether every BUSY clear updates it uniquely. The 24 MHz comment is a rate hint, not evidence that a saved value marks command completion or can be compared directly with a CPU counter sample. A source definition cannot retrospectively qualify the ABI 2 BUSY words.

A separate native calibration would use the normal cpufreq interface to provoke controlled distinct-state and no-op requests on **both** clusters, without adding an idle-policy wait or direct hardware-register write. A bounded observer would retain raw command, status and `+0x38` reads with physical-counter brackets before submission, around BUSY assertion/fall, and after settling, plus every writer, read error and lost sample. The review would test update edge, repeatability, width and wrap, counter relation, read stability, and autonomous/no-op changes. Even consistent finite samples would establish behavior under tested conditions, not a universal no-clear/reassert invariant.

Only after such calibration could a new WFI experiment test a declared bridge, with complete SET accounting and a measured read-to-WFI/return interval. An unchanged timestamp across two BUSY-positive reads would still need proof that distinct completions cannot alias that value. A calibrated completion timestamp strictly after a verified WFI return could support a stronger temporal claim only if the timestamp belongs to the same recorded command and an earlier clear/reassert cycle is excluded; a timestamp within the entry-to-return bracket would remain ambiguous. The existing capture cannot establish or sensitively refute instruction-time BUSY, and issue #5 remains open.

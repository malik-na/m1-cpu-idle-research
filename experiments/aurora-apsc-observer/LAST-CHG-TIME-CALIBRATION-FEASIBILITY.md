# Can `LAST_CHG_TIME` bridge an APSC BUSY read to WFI?

**Static feasibility review, 4 October 2026; no register read or new native capture.** The target is the T8103/J313 Aurora research line used by the [ABI 3 E packet](ABI3-E-TICKET-RESULT.md), not a claim about the machine's current boot. E contains 18 ticket-ordered software final-entrant witnesses with APSC BUSY set at the first-attempt **pre-DSB read**. Its linked code still executes instructions between that read and `wfi`; one witness's closest peer exit is only one ticket after the read bracket. The [prior timestamp audit](LAST-CHG-TIME-AUDIT.md) and [instruction-boundary audit](WFI-INSTRUCTION-BOUNDARY.md) already establish that no saved packet reads `LAST_CHG_TIME` or proves BUSY at the instruction. This note asks only whether a *new* calibration is a credible route to the missing temporal bridge.

## What the primary sources permit

The pinned [Aurora T8103 cpufreq source](https://github.com/iconidentify/aurora-linux/blob/90a95335a49aec3a0045a76da140452ad6585eb3/drivers/cpufreq/apple-soc-cpufreq.c#L25-L36) and [Asahi source](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L25-L36) define `APPLE_DVFS_LAST_CHG_TIME` at cluster-resource offset `0x38` and annotate a 24 MHz CPU-counter timebase. The [original driver submission by its author](https://lkml.iu.edu/hypermail/linux/kernel/2205.0/02962.html) likewise defines the offset but uses the command register at `+0x20` to poll prior BUSY clear and submit SET; it does not read or interpret `+0x38`. The pinned [cluster-cpufreq binding](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/Documentation/devicetree/bindings/cpufreq/apple%2Ccluster-cpufreq.yaml) describes a per-cluster DVFS resource and performance-state indices, without a field-level timestamp contract. The pinned [m1n1 P-state implementation](https://github.com/AsahiLinux/m1n1/blob/ce2b8a43cea4220b602af1005dc9dbfc59c9624e/src/cpufreq.c#L79-L123) polls command BUSY after its SET and supplies no `+0x38` interpretation.

The [Arm Generic Timer guide, §§3.1 and 4](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Generic%20Timer.pdf?revision=c710e7a7-9f52-4901-8c9d-91b19f44f9c7), documents `CNTPCT_EL0` as the system count, warns that its reads may be speculative unless ordered (for example with `ISB`), and says the SoC implementer defines its particular counter implementation. That architecture guidance constrains **how to bracket** a candidate read; it does not define Apple's APSC register. A matching 24 MHz rate alone does not establish an equal epoch, width, wrap rule, update event, or atomic relation to BUSY. The reviewed source and official guide therefore provide **no completion or continuity invariant** for `+0x38`. This is a bounded conclusion about these cited artifacts, not a claim that no unpublished Apple specification exists.

## A discriminating, bounded native calibration

On a separately qualified observation-only helper or image, first recheck the live T8103 resource, kernel/build/configuration, cpufreq policies, counter frequency and fallback. Establish an independently justified access width and read-safety basis for `+0x38` **before the first read**; if neither is available, stop without hardware access. The register's name does not establish that reads are side-effect-free, and stopping after an error cannot undo an earlier read side effect. A guarded, default-off reader would use the mapped cluster resource, never add a direct MMIO write or an idle-path wait. Ordinary cpufreq requests may cause the existing driver to emit its usual SET writes. Use a small fixed number of **verified driver SETs** on each cluster, including settled distinct-pstate transitions and, if the driver permits them, same-pstate SETs. Keep requests suppressed before SET as a separate no-SET control; they do not test a hardware same-pstate update. Include quiet intervals and stop on an access fault, error, unexpected device behavior, or missing record.

For every qualified trial, retain the raw command/BUSY word, current/target status, raw `+0x38` word and chosen read width, issuing CPU and policy/cluster, SET sequence, ordered physical-counter brackets around **each** register read, sampling phase (before SET, BUSY seen, BUSY clear, settled), and all failures, losses and unaccounted writers. Exclude a trial from update-edge classification if any background SET, other possible writer, or relevant loss occurs between its brackets; preserve it as an ambiguous result. The driver permits a SET from a CPU outside the target cluster, so a same-CPU stream alone is insufficient. Compare a limited read-rate control for measurement disturbance. The falsifiable distinctions are: update at SET submission, at observed BUSY fall, only at actual pstate change, during no-SET quiet time, or not reproducibly at all. Record whether changes fit one fixed counter offset and a consistent modulo width; equal rates do not substitute for this check. Distinct SETs that complete inside one 24 MHz tick can alias even if the register records completion, so quantify such collisions rather than treating equal values as continuity.

Passing finite trials would show a *local empirical relation* for tested requests, not that every possible controller/firmware action updates exactly once or that BUSY cannot clear and reassert between two reads. To bridge a future pre-WFI BUSY sample at time `t_read` to execution at `t_wfi`, the method would still need to identify the **same outstanding command**, prove its completion timestamp is strictly later than `t_wfi`, exclude intervening clear/reassert and other writers, and place that timestamp against an independently bounded instruction/return time. A timestamp later than a verified WFI **return** could support such ordering if all those premises held. A timestamp inside the entry-to-return bracket, an unchanged timestamp, or the existing E packet cannot locate BUSY at the instruction. Neither result establishes peer physical sleep, rail power, energy, or an idle-policy benefit. If the calibration cannot validate the invariant, pursue an independently qualified instruction-correlated command-state observation rather than reinterpret E's pre-DSB witnesses.

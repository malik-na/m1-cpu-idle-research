# EL2 WFI trapping is an instruction-correlated guest diagnostic

This is a static feasibility assessment for [issue #5](https://github.com/malik-na/m1-cpu-idle-research/issues/5), not an implemented or run experiment. The target remains the T8103/J313 Linux research boot, but a tethered m1n1 hypervisor boot would be a **different execution environment**. The accepted ABI 2 result reads APSC BUSY on a first attempt before `dsb sy; wfi`; its [linked-code audit](WFI-INSTRUCTION-BOUNDARY.md) places 13 instructions between that read and WFI. ABI 3 tickets can establish software peer order at the same pre-DSB read, not command state at WFI.

The Arm architecture provides a possible instruction-correlated trigger: `HCR_EL2.TWI` traps an EL0/EL1 WFI to EL2 with exception class `0x01` **if the instruction would otherwise enter a low-power state**, subject to the documented higher-priority controls. It does not promise one trap for every executed WFI. See [Arm DDI 0600B.a, `HCR_EL2.TWI`](https://documentation-service.arm.com/static/62c410c8b334256d9ea8dffb). The pinned [m1n1 register definitions](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/arm_cpu_regs.h#L58-L60) include the `0x01` syndrome and [TWI bit 13](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/arm_cpu_regs.h#L173-L177). Its [default hypervisor HCR setup](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv.c#L140-L147) omits TWI, and the [synchronous exception dispatcher](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv_exc.c#L486-L563) has no WFI case. Simply setting the bit would therefore fall through to its proxy exception path; a target-side handler would have to be built and reviewed.

A bounded prototype could enable TWI on every guest CPU and record `ESR_EL2`, guest `ELR`, CPU, counter brackets, and one read of that cluster's DT-qualified APSC command address into a preallocated target-side buffer. It would accept only a syndrome identified as WFI whose `ELR` matches the linked `apple_cpu_deep_wfi` WFI PC, including retries; the `0x01` exception class covers WFI and WFE, so syndrome/guest instruction validation is necessary. The handler would need a reviewed EL2 MMIO mapping, live HCR readback, loss accounting, and a no-host-callback fast path. These are implementation requirements, not present capabilities or results.

The trap is taken **instead of completing that guest WFI**. A command read inside the handler occurs after exception entry and can race controller progress or another CPU's SET. Advancing `ELR` would skip the guest WFI; returning to the same `ELR` with TWI still enabled would trap again. Letting the guest execute it requires a separately designed temporary trap disable and rearm mechanism, which still leaves a read-to-WFI interval. An EL2 WFI substitute would also execute in a different interrupt and power context. Thus even a BUSY record with the exact guest WFI PC would mean “BUSY at an EL2 read after a trapped guest WFI attempt,” **not BUSY at an actually executed native Linux WFI**. The pinned [m1n1 interference audit](../../notes/trace-validity.md) documents further guest power, timer, CPU-state, and transport differences.

This route can diagnose whether a guest reaches a sleep-eligible WFI PC near an outstanding command. It cannot close issue #5's native instruction-state criterion without an independently validated BUSY-continuity/completion bridge or a qualified concurrent hardware command-state observation. Enabling TWI changes a hardware control register and the idle path, so any test needs its own protocol and controls under the issue's observation-only boundary; it is not a repeat of the accepted native ABI 2/3 capture.

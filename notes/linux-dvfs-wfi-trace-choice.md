# Choosing an observation-only Linux DVFS-to-WFI capture

Research decision for [Choose an observation-only Linux DVFS-to-WFI trace](https://github.com/malik-na/m1-cpu-idle-research/issues/3) and [experiment E2](../wiki/Experiment-Backlog.md), 2026-10-01. This is a source-pinned design, **not** a kernel patch or a native observation. No root session, reboot, hardware access, or register write was performed for this note.

## Decision and testable outcome

Use a staged, opt-in capture on the **actually booted T8103 Linux build**. First record stock `power:cpu_idle` and `power:cpu_frequency` as a software-timeline and trace-overhead control. To answer the issue's command question, use fixed-size, preallocated records at the Apple cpufreq command write and at the Apple deep-WFI entry path. Start with a **noinstr-safe** C sample before `ct_cpuidle_enter()`; only if its observation-to-WFI gap prevents interpretation, review a tiny first-attempt AArch64 sample after the power-control `msr` and before the WFI retry label. Do not add a wait, post-submission read, new command write, or power-control change. [Apple cpufreq write](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L171-L207), [Apple idle callback and assembly](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L21-L94).

The falsifiable question is whether a candidate final core samples command bit 31 (`BUSY`) set after a recorded SET submission for its cluster, including a submission by another cluster. Repeated no-BUSY samples under controlled opportunities, with bounded loss and measured probe sensitivity, would weaken that hypothesis. Either result is about **command state at a sample point**, not rail-off time, a Linux defect, or an energy saving.

## Why stock tracing alone cannot answer it

The cpuidle core emits `trace_cpu_idle(index, dev->cpu)` **before** calling the selected driver's `enter()` callback and emits the exit event after it returns; these events neither mark the actual WFI instruction nor read the command register. [Pinned cpuidle core](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle.c#L245-L283). The fast-switch path updates `policy->cur` and emits `trace_call__cpu_frequency(freq, cpu)` for policy CPUs **after** the driver callback. Those CPU fields identify targets, not necessarily the executing writer CPU, and the event contains no command BUSY value. [Pinned cpufreq core](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/cpufreq.c#L2198-L2220). A kprobe/ftrace callback in the idle interval would add substantial instrumentation and must not be treated as a zero-cost instruction-level marker; the direct ring avoids such callbacks there. Stock tracepoint loss still needs accounting.

## Smallest probe seams

| Seam | Record without altering control | Limit |
|---|---|---|
| In `apple_soc_cpufreq_set_target()`, immediately around its existing `writeq_relaxed()` | Existing pre-write command read, requested pstate/index, exact SET word, issuing logical CPU, target policy/cluster and mask, timestamps before/after the write, timeout/error result | The driver waits for an **older** BUSY to clear, writes the new command, then returns; never add a post-write read to this first variant. [Driver lines 171–207](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L171-L207). |
| In `apple_enter_idle()` after successful `cpu_pm_enter()` and before `ct_cpuidle_enter()` | Entry state, logical CPU/cluster, bounded read of that cluster's command word, timestamps bracketing the read, error and record sequence | This is **pre-WFI**, with a gap including context transition and assembly setup. The entire `apple_enter_idle()` function is `__cpuidle`, which the pinned kernel maps to an uninstrumented section. Being before `ct_cpuidle_enter()` does **not** make an ordinary C helper safe: use reviewed inline/noinstr-safe operations or a precisely bounded `instrumentation_begin()`/`instrumentation_end()` region there, and pass objtool/noinstr checks. No ordinary instrumented helper may run in the RCU-idle region. [Driver lines 68–94, 110–119](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L68-L119), [`__cpuidle` definition](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/include/linux/compiler_types.h#L435-L453), [core contract](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle.c#L258-L270). |
| Escalation only: tiny AArch64 sample **before** `apple_cpu_deep_wfi` label `1:`, after the power-control `msr` | One first-attempt command read bracketed by physical-counter samples, BUSY bit, CPU/cluster, sequence; a return record after the RCU-idle interval | The existing `cbz x0, 1b` retries at label `1:`, bypassing this sample. It therefore records only the first WFI attempt; do not describe it as every retry or as a sample at every WFI. Preserve saved registers, stack alignment, sysreg writes, original DSB/WFI and retry semantics; inspect the compiled instructions. [Assembly lines 21–58](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L21-L58). |

Use the target kernel's supported physical-counter read (`CNTPCT_EL0` or its arm64 helper), record `CNTFRQ_EL0`, and test ordering across E/P CPUs before comparing remote events. The pinned arm64 implementation provides explicit physical and virtual counter helpers with ordering choices; do not assume the local Mac's earlier 24 MHz observation describes every boot or source revision. [Pinned arm64 timer implementation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/include/asm/arch_timer.h#L65-L85).

## Record integrity and observer effect

Preallocate bounded normal-memory streams before capture, with unique reservation/commit sequence numbers, explicit overflow/drop counters, and an error record for a failed cpufreq poll or unavailable mapping. A per-CPU ring alone does not guarantee safe publication if a writer is nested or migrates; review atomic reservation and the reader's acquire/release contract for both fast-switch and slow-worker contexts. Stop recording on full capacity, never wait for space, and export only after the bounded interval. Store raw command words alongside decoded BUSY and preserve attempt indices. Reconstruct a **candidate software final entrant** offline from per-core entry/return intervals; do not put a global last-core lock/counter in the hot path. The driver permits DVFS from any CPU, so record writer CPU separately from target policy and its online/related masks. [Policy flags](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L304-L317), [remote-update permission](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq.c#L61-L75).

Resolve the idle reader's MMIO pointer from the **booted device tree** at setup time and prove its lifetime: the cpufreq driver maps the performance domain during policy initialization and unmaps/frees it at policy exit. Do not dereference `policy->driver_data` dynamically in the RCU-idle window or hard-code the macOS physical addresses. [Mapping](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L210-L235), [policy exit](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L332-L340). A safe shared-mapping or separate read-only mapping arrangement needs an explicit hotplug/teardown review before any patch is run.

Predeclare three matched short variants: disabled baseline, normal-memory records without idle MMIO, and records plus one idle MMIO read. Capture a quiet interval and controlled same-cluster/remote-writer opportunities, with identical completed work. The extra MMIO read, record stores, counter barriers, and original `dsb sy` may delay WFI or change write delivery; a no-BUSY result in the sampled variant does **not** prove no uninstrumented overlap. Report all incomplete/overwritten events, per-stream drops, timestamp reversals, and min/median/tail probe cost from the bracketed samples. Do not use traced power as an untraced energy baseline. [Linux I/O-ordering documentation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/Documentation/driver-api/device-io.rst), [original WFI barrier](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L37-L42).

## Identity and go/no-go before a future native run

Capture the running `uname`/kernel build and config, exact source commit, booted DT blob or hash and CPU `performance-domains`, m1n1/bootloader identity, `apple_idle` registration and per-core state enablement, each cpufreq policy's related/online CPU masks, driver, governor and requested/actual frequency interfaces. Record `fast_switch_enabled` from the **runtime policy** via a setup-time observation; source `fast_switch_possible = true` is only capability. The pinned schedutil code has both fast and deferred paths, and the latter's worker is restricted to policy-related CPUs, so identify the active path before interpreting a remote writer. [Policy flags](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L304-L317), [schedutil fast/shared branches](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq_schedutil.c#L515-L541), [slow-worker affinity](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq_schedutil.c#L677-L707). If these identities differ from the pinned source, re-audit the seams before proceeding.

Before testing on hardware, cross-build and inspect the AArch64 object, run the target tree's relevant noinstr checks, verify the fixed record bounds and mapping lifetime, and confirm there are no added MMIO writes or polling loops. Do not load or boot this design until a separate authorized native experiment has an explicit fallback. This note selects an observation strategy; it establishes neither an overlap nor a Linux behavior change.

# Native PCPM state signal: calibration decision

Research note for [Choose a native physical-state signal for the APSC question](https://github.com/malik-na/m1-cpu-idle-research/issues/4) and [experiment E3](../wiki/Experiment-Backlog.md#e3--find-an-independent-native-physical-state-signal), 1 October 2026. This is a plan for a later **native T8103 Linux** observation, not a measurement. No MMIO read, boot change, or power-state write was made for this note. The [observable audit](idle-observable-audit.md) supplies the local ADT mapping and safety analysis.

## Decision and claim boundary

Use the PCPM entry in the T8103 PMGR PS3 bank as the first candidate: parent-bank offset `0x48`, physical address `0x23b700048` **for the captured mapping only**. Save the entire 32-bit word; decode `ACTUAL = (raw >> 4) & 0xf` and `TARGET = raw & 0xf` afterward. The saved [ADT device map](raw/pmgr-device-map.json) assigns PCPM `psreg=3, psidx=9`; the pinned [T8103 DTS](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8103.dtsi#L1049-L1054) places bank 0 at `0x23b700000`; [m1n1's PS3 decoder](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hw/pmgr.py#L4-L28) defines the fields and ten eight-byte slots.

The pinned [Linux PMGR driver](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L20-L36) calls `0xf` active, `0x4` clock-gated, and `0x0` power-gated for its PMGR state domains, and [polls `ACTUAL` separately from target](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L98-L114). Those are useful decoder labels, **not yet a calibration of what PCPM codes mean for CPU-cluster rails**. The [T8103 PMGR child DTS](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8103-pmgr.dtsi) lists domain controls starting at `0x100`, not a PCPM child at `0x48`. A successful read establishes only “PMGR reported PCPM `ACTUAL=N` at the sampled instant.” Bits 8/9 are named `WAS_PWRGATED`/`WAS_CLKGATED` in both decoders; their latch and clearing behavior is uncalibrated, so retain them in `raw` and derive no entry count or residency from them.

## Falsifiable calibration sequence

First recheck the **booted** board, kernel commit/config, DT PMGR resource, m1n1/firmware and PMGR-regmap ownership. Abort if they differ from this T8103 mapping. Use a bounded, read-only kernel collector sharing the verified PMGR mapping, executing on an E core. Each preallocated record is `{monotonic_before_ns, monotonic_after_ns, cpu, raw, read_errno, sequence}`; also retain sample schedule, clock units, overflow/drop count and the independently timestamped per-P-core software idle intervals. A read interval brackets an asynchronous state machine, not an atomic transition timestamp. The existing [audit](idle-observable-audit.md#smallest-later-native-c-acquisition) gives the minimal `regmap_read(map, 0x48, &raw)` seam. Linux [device-I/O documentation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/Documentation/driver-api/device-io.rst) explains why an integer-address dereference or conflicting cacheable mapping is inappropriate.

| Condition, in repeated fixed-length windows | Discriminating result | Competing explanation / failure |
| --- | --- | --- |
| All P cores doing pinned, completed work | Establish the active reference code and read success; `0xf` is the decoder's predicted label. | A different stable code means the generic label does not transfer cleanly to PCPM. |
| One P core active, other P cores in software `CPU PD` | If PCPM still reports the active reference, that is consistent with a cluster-level signal. | It does not establish that individual P cores gated. |
| All four P-core `CPU PD` intervals overlap, then a controlled P-core wake/recovery | A repeatable distinct `ACTUAL` code during settled overlap, followed by the active reference on recovery, supports a useful PMGR state discriminator. Keep raw `TARGET` and unknown/intermediate codes. | Constant active, read errors/stalls, or changes only at wake boundaries weaken this candidate; software overlap alone does not prove a physical state. |

Predeclare a guard interval around software entry/exit boundaries and report sensitivity to that guard. Use sparse samples with varied phase relative to the workload, not a tight polling loop; otherwise periodic wakeups and missed short states bias apparent occupancy. Once [E1 and E2](../wiki/Experiment-Backlog.md) establish their own APSC/BUSY event timing, align those events with PCPM samples without moving the reader into the last-core path. Temporal association alone would not prove that pending DVFS caused a state change. A code change establishes a **PMGR-reported state**, not rail-off, exact transition time, or energy. A constant code cannot disprove all deeper states: the state machine may not expose them here, or the observer may prevent them.

## Observer-effect gate and fallback

Keep capture on an E core, with no P-core IPIs, printing, allocation or remote streaming inside the sample loop. Compare matched windows with (A) no collector, (B) E-core timing/logging without the MMIO read, and (C) sparse PCPM reads; then vary C's cadence and phase in randomized or reversed order. Preserve delivered work, P-core software idle, wake latency, battery/AC and USB/display state, thermal trend and loss. If C changes idle/energy beyond B, or read latency/errors increase when P cores appear idle, treat the register as an invasive observer and stop using it as a residency estimator. If no change is detectable, report the experiment's sensitivity rather than calling the read proven inert. Both [m1n1](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/pmgr.c#L87-L98) and [Linux](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L57-L63) use ordinary status reads, but neither source guarantees zero fabric-power cost in an idle P cluster.

If PCPM is constant, inaccessible or observer-sensitive, use an **independent native energy-and-wake route**: an external supply/battery instrument, or a verified battery `energy_now`/charge counter if the booted driver exposes one, with no PMGR sampling during measured windows. The pinned [Linux power-supply ABI](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/Documentation/power/power_supply_class.rst) defines units but explicitly allows devices to omit properties; availability and resolution must be checked on this Mac. An idle-versus-load comparison under unchanged Linux is descriptive, **not a causal APSC-policy test**. Only after [Set the evidence gate for an opt-in Linux wait experiment](https://github.com/malik-na/m1-cpu-idle-research/issues/8) permits a bounded, opt-in wait experiment should a matched-work A/B/B/A policy comparison define **A = unmodified native Linux** and **B = the same pinned base tree, configuration and firmware with only the opt-in wait-policy variant enabled**. Retain wake correctness/latency, delivered work and environment for both. Such a comparison can test a **whole-system energy and wake consequence**, not identify a P-cluster rail state or isolate CPU watts. The P-core `cpu-impl-reg + 0x100` status is not a drop-in backup: [m1n1's stop path](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/smp.c#L214-L249) says last-core deep sleep can remove register access. A rail-off claim therefore remains open until a separately characterized physical signal or rail measurement exists.

# Linux DVFS requests versus M1 deep idle: bounded concurrency review

Date: 2026-10-01. This is source analysis and an instrumentation proposal. No kernel patch was applied, compiled, booted, or run for this review. No hardware policy was changed.

The inspected Linux path permits an outstanding DVFS request when a CPU reaches `apple_cpu_deep_wfi()`. Its synchronization serializes software frequency requests; it does not establish that the request just submitted has finished before idle. A CPU in another policy can also submit a request for a cluster whose CPUs are entering or already in software idle. These are permitted timelines, not proof that they occur on this machine, prevent physical power collapse, or require a Linux fix.

The macOS conditional last-core wait therefore has a concrete observation target: is command bit 31 set shortly before Linux's deep WFI, and which CPU submitted the request? Adding a wait immediately would skip the most useful experiment and could still leave a check-to-WFI race with remote writers.

## Source identity and scope

Both requested Asahi Linux revisions were inspected:

- `77cb8f24c2381a8abb7272d7bbdec548d6426a8a`
- `94fb23346d522edf53722357c426a3e58030beea`

The 17 selected files are byte-identical between those revisions, including the Apple cpufreq and cpuidle drivers, schedutil, cpufreq core, scheduler idle and fair paths, CPU PM notifiers, and arm64 I/O primitives. Their URLs and SHA-256 provenance are in [concurrency-sources/manifest.json](concurrency-sources/manifest.json); third-party source copies are not included in this public repository. Links below use the first revision; the equivalent second-revision files have the same content. This does not establish the source identity, configuration, governor, or fast-switch enablement of a currently booted Linux kernel.

The existing native reports showing all eight CPUs overlapping in software CPU PD, with no menu/teo power benefit, are supplied context. This review does not revalidate those reports or restart a governor investigation. Software entry accounting cannot identify the hardware's actual cluster collapse boundary.

The macOS comparison is the conditional last-core path documented in [review.md](review.md) and the subsequent flag audit in [local-driver-skipflag-followup.md](local-driver-skipflag-followup.md). The latter predicts that the wait is enabled from the absent `cpu-tvm` property and zero-initialized allocation; it is still a static prediction, not a live observation of the branch.

## What synchronization actually establishes

| Path | Established by source | Not established |
|---|---|---|
| Apple `set_target()` | Poll command BUSY clear before issuing its new SET write; then return | Completion of that newly issued request |
| Shared-policy schedutil fast switch | `update_lock` serializes requests for the policy | Mutual exclusion with cpuidle or physical transition completion |
| cpufreq fast-switch core | Requires governors to exclude concurrent same-policy callbacks; updates software frequency bookkeeping after callback | A hardware status read after Apple's write |
| Slow cpufreq path | Worker mutex and core transition bookkeeping serialize software operations | A post-request completion barrier with cpuidle |
| Idle entry | Local IRQ disabling and reschedule checks; CPU PM notification; original `dsb sy; wfi` | Exclusion of a CPU in another cluster, or an explicit command BUSY check |

`apple_soc_cpufreq_set_target()` reads command offset `0x20` until bit 31 is clear, updates requested pstate fields and SET bit 25, performs one `writeq_relaxed()`, and returns. The 400 microsecond timeout bounds the **preceding** busy wait; it is neither a mandatory dwell nor a wait for this new write. `fast_switch()` returns the requested frequency from the table after this callback succeeds. It does not read the actual current pstate. [Apple driver, lines 171–207](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L171-L207)

For a shared policy, schedutil holds `sg_policy->update_lock` across its fast-switch call. The core API contract excludes simultaneous same-policy frequency callbacks, but the Apple callback's return still follows submission, with no post-write poll. `policy->cur` and frequency trace events are therefore software bookkeeping, not proof that BUSY has become clear. Fast-switch capability is set by the driver, but actual `fast_switch_enabled` must be collected on the target: capability alone is insufficient. [schedutil shared update](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq_schedutil.c#L516-L541), [fast-switch contract and implementation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/cpufreq.c#L2176-L2222)

The Apple driver sets `dvfs_possible_from_any_cpu = true`. The scheduler's permission function accepts a CPU outside the target policy if that flag is set and the issuing CPU has an active update-util hook. This explicitly permits cross-policy fast-switch requests; the target CPU's local interrupt mask cannot exclude them. [Apple policy initialization](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpufreq/apple-soc-cpufreq.c#L304-L317), [permission test](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq.c#L60-L76)

`cpu_pm_enter()` invokes generic state-preservation notifiers, then releases its notifier lock. The Apple cpufreq driver does not register a CPU PM notifier in the inspected file. Nothing in these paths supplies a shared frequency/idle lock. This is a bounded finding about the inspected paths, not an exhaustive proof about every platform notifier in an arbitrary kernel configuration. [CPU PM implementation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/cpu_pm.c), [Apple idle entry](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L68-L94)

The deep-idle assembly changes the existing CPU power control bits, executes `dsb sy; wfi`, and repeats WFI on return if `ISR_EL1` reports no pending interrupt. There is no DVFS MMIO access or software last-core handshake in this driver. A DSB's architectural memory-access completion guarantees must not be equated with “the device has completed a frequency transition”: the latter needs a device-specific contract, absent here. Even a non-posted mapping can complete a register write while the device remains busy doing what was requested. This review does not assert that the existing barrier is incorrect. [Idle assembly](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/cpuidle/cpuidle-apple.c#L21-L58), [I/O mapping and access semantics](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/Documentation/driver-api/device-io.rst), [arm64 I/O implementation](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/include/asm/io.h)

## Concrete permitted timelines

**A. The last active CPU submits a request, then becomes idle.** Other CPUs in the policy have already entered software CPU PD. The remaining CPU runs a scheduler utilization update, passes the old BUSY-clear test, writes a new SET request, returns through schedutil, and schedules its idle task. After CPU PM notification it enters the deep-WFI assembly. If the device transition lasts longer than that software tail, BUSY can still be set at entry. No inspected lock forbids this ordering. Whether that duration inequality holds on M1 needs observation; source alone does not answer it.

**B. Another cluster issues a request while the target cluster is idle.** An idle load balancer walks `nohz.idle_cpus_mask`, including remote CPUs. `update_nohz_stats()` can invoke `sched_balance_update_blocked_averages(remote_cpu)`, which locks that remote runqueue and, when averages decay, calls `cpufreq_update_util(remote_rq, 0)`. The hook is selected from the target runqueue's CPU, while the issuing CPU may be in the other cluster. With schedutil fast switching enabled, its rate-limit/frequency-change checks satisfied, and the Apple's any-CPU permission accepted, the executing CPU can write the target policy's DVFS command. [Remote idle iteration](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/fair.c#L12971-L13060), [blocked-average update](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/fair.c#L10237-L10258), [hook selection](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/sched.h#L3497-L3505)

This route can overlap the target's idle entry or occur after its CPUs have entered software idle. It does not require an IPI that makes a target CPU execute the driver's write. It is conditional, not inevitable: decayed load may resolve to the existing frequency, the rate limit may reject it, or fast switching may be disabled. The idle balancer itself being outside the target policy and the actual online/policy masks also require target evidence.

This timeline matters to any proposed fix: a final-core BUSY-clear sample followed by WFI has a check-to-entry window. A remote request could arrive after the sample. Two successful clear samples, as in the macOS code, do not by themselves close that window. macOS may have additional writer coordination or hardware semantics that this local comparison has not established.

**C. Slow switching does not automatically remove the tail.** If fast switching is disabled, `sugov_work()` calls the same Apple `target_index` callback under `work_lock`. That callback still returns immediately after its write. The worker can finish its work and sleep, allowing its CPU to become idle before hardware completion. The schedutil worker is restricted to `policy->related_cpus` in this source, including the any-CPU case; it would be wrong to reuse timeline B as an assertion that this worker normally writes from another cluster. [Slow work and mutex](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq_schedutil.c#L544-L568), [worker affinity](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/kernel/sched/cpufreq_schedutil.c#L677-L707)

## Reasons the macOS wait could be redundant on Linux

- Hardware may defer collapse until an in-flight transition finishes, or safely complete DVFS while cores sleep. A software request/idle overlap then need not waste energy or cause a correctness problem.
- The request could always finish before the Linux entry sequence reaches WFI under the tested operating conditions.
- Linux's boot-time hardware configuration and macOS's control sequence may differ. The macOS wait may be paired with another macOS-specific operation, firmware requirement, or workaround.
- A command BUSY flag may indicate command acceptance/protocol work whose relationship to physical cluster gating is weaker than its name suggests. Linux and macOS checking the same bit supports register identity, not complete hardware semantics.

None of these alternatives is resolved by all-eight software CPU PD overlap, requested frequency traces, the cpufreq transition latency metadata, or the static presence of the macOS wait. Existing software synchronization does **not** prove redundancy; undocumented hardware behavior still might.

## Smallest observation-only instrumentation proposal

The first implementation should answer occurrence and attribution, without introducing a busy wait, holding a new lock across idle, changing the governor, or writing a new hardware control value. Two observation seams are sufficient:

1. **DVFS submission:** In `apple_soc_cpufreq_set_target()`, retain the command value already read and record the command value about to be written, issuing logical CPU, target policy/cluster, requested pstate, and timestamps bracketing the existing write. Record timeout failures separately. Do not add a post-write MMIO read in this first variant: readback itself can affect write delivery and timing. Keep the existing write count, width, value, and ordering unchanged.
2. **Deep-WFI entry:** Obtain an initialized, lifetime-pinned pointer to that CPU's cluster command register and its private record storage before entering the RCU-idle region. In the assembly, immediately before the original `dsb sy; wfi`, take a bounded command read and counter sample, store a fixed record, then execute the original DSB and WFI unchanged. Do not put new record stores after the original DSB, since that would leave the new stores outside its coverage. Record return timing after leaving the RCU-idle region. An initial C-only variant immediately before `ct_cpuidle_enter()` is simpler and sufficient to identify a pending request on the entry path, but has a larger observation-to-WFI gap.

Use C for initialization and export, with a small, inspected AArch64 sequence for the entry sample. Do not call printk, tracepoints, allocation, locks, firmware interfaces, scheduler helpers, or ordinary instrumented C from the assembly/RCU-idle interval. Preserve the existing register saves, stack alignment, power-control writes, ISR test, barriers, and WFI retry behavior. If only the first WFI attempt is recorded, label it as such: one driver invocation can execute several WFIs. Recording every retry needs bounded ring handling and a distinct attempt index; it must not accidentally turn a full ring into a wait.

Use fixed-size, preallocated per-CPU records with explicit sequence/overflow accounting and separate submission/idle streams. Publication and reentrancy rules must be specified for both fast and slow cpufreq contexts; a per-CPU ring alone does not make nested or migrating writers safe. Prefer capture while CPU hotplug and policy teardown are excluded by setup/lifetime management, with no new hot-path exclusion. After the bounded run has stopped, export the records through a deferred reader. A reader should not wake periodically or consume console bandwidth during capture.

Record target cluster identity, writer CPU identity, policy masks and online masks, exact kernel/build identity, fast-switch state, entry/return phases, command bits, and counter units. Cross-CPU counter comparability must be checked before ordering remote events. The source's 24 MHz comment is useful provenance, not a substitute for recording the target counter frequency. Correlate per-CPU software entry/return intervals offline to identify a **candidate** final entrant; do not add a contended global active-core counter to the first observation patch, and do not call the reconstructed software state physical power collapse.

The register mapping must follow the target device tree/cpufreq resources; do not hard-code local macOS physical addresses into Linux. Sharing a cpufreq mapping with idle requires an explicit lifetime contract: the current cpufreq exit function unmaps and frees it. Built-in test configuration and setup-time policy references may simplify this, but must be reviewed. No `driver_data` lookup or dynamic lifetime acquisition should occur in the RCU-idle interval.

An MMIO observation is not neutral. It may complete a posted write, keep an interconnect active, delay WFI, or let the transition finish. Normal-memory records add cache traffic, and the existing DSB may wait for those stores. Preserve a disabled baseline, a record-only control, and an MMIO-sampling variant to bound the observer effect. A positive BUSY sample proves pending state at that sample point. A negative run does not prove that the original uninstrumented path never overlaps. Neither result alone establishes a power saving.

## Required validation before any native experiment

- Pin the actual native Linux kernel source, configuration, device tree, cpufreq policies, governor, and fast-switch enablement. If it differs from these snapshots, repeat the narrow path audit for that source.
- Cross-build the instrumented arm64 drivers against each selected revision and the target configuration. Review warnings, `__iomem`/sparse diagnostics, CPU hotplug and module lifetime, and the exact AArch64 object code. Verify no extra MMIO writes, power-control changes, new polling loop, unbounded ring logic, or instrumentation/runtime calls inside the idle interval; run applicable noinstr validation available in that tree/toolchain. Preserve the existing ABI, register state, and stack alignment.
- Keep this a bounded native observation with a known boot fallback and the already established T480 capture arrangement. Capture records after the test interval rather than streaming from the idle path. Validate record integrity, lost-event counts, timestamps, and cross-policy attribution before interpreting a timeline.
- Separate subsequent power qualification from these traced runs. Do not interpret a power change caused by MMIO sampling or record traffic as evidence for a prospective wait policy. A wait-policy experiment is a later decision, contingent on an observed overlap and a credible hardware consequence.

The useful next result is a timestamped submission-to-entry timeline, particularly a remote-policy write or a BUSY sample near a candidate last-core entry. The available source evidence justifies that observation. It does not yet justify a Linux correctness report, a power-management fix, or a claim that the mechanism was previously unknown to Asahi or Aurora Silicon.

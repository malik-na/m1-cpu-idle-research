# Faster T8103 CPU-idle reverse engineering

Research date: 2026-10-04. Target: base-M1 T8103/J313. This is a source-backed workflow proposal; it adds no boot, register read, power-policy change or hardware result. The staged #6 PS3 image still needs its first native records-only boot. The operator's instruction to stop further #5 reboots remains in force.

The useful speed improvement is to make each experiment eliminate a specific explanation, then reuse the resulting infrastructure. More register access alone would increase ambiguity. Read the existing [hypervisor validity audit](trace-validity.md) and [non-reboot investigation](../wiki/Non-Reboot-Investigation.md) before selecting an observation route.

## What to improve first

1. **Maintain a register evidence table.** For each candidate, record the exact target, address/resource, width, source revision, known access path, decoder, ownership, observed raw values, semantic confidence and next falsifier. Keep a known field layout separate from a calibrated physical meaning. m1n1 describes PS3's ten eight-byte slots and `ACTUAL`/`DESIRED` fields, while Linux's generic PMGR driver defines active/clock-gated/power-gated codes and polls its managed domains. Those sources do not calibrate the CPU slots as physical core rails. A naturally occurring transition of an already Linux-managed peripheral can qualify an accessor/decoder, but cannot transfer that peripheral's semantics to PCPU. [m1n1 register definitions](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hw/pmgr.py#L4-L35), [managed-domain driver](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L20-L36), [driver transition/readback](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/pmdomain/apple/pmgr-pwrstate.c#L56-L126).
2. **Develop a reusable native research kernel.** Proposal for a later reviewed revision: default-off, fixed register allowlists, existing-map-only access, preallocated records, hard read caps, explicit mode/state checks and a safe way to start a new isolated block. This could separate baseline, records-only and sparse-MMIO blocks without rebuilding for every workload. Validate reset/dormancy and instrumentation effects first; reuse never makes carry-over or matched controls disappear. The current #6 instrument is deliberately one-shot per boot, so its [records-first and fresh-boot MMIO gates](../experiments/linux-pcpm-sampler/PCPU-PS3-PROTOCOL.md) still apply.
3. **Prepare everything outside the hardware window.** Parallel agents can audit source and exact-build disassembly, develop decoders/exporters against fixtures, review protocol falsifiers, and publish sanitized packets. One coordinator owns live access and the experiment schedule. Deliver a small matrix with a stop rule before rebooting: which outcomes advance calibration, and which retire the candidate. The current PS3 protocol already distinguishes access qualification, variability and balanced per-core confirmation; complete those gates rather than treat the first changing word as a discovery. [PS3 protocol](../experiments/linux-pcpm-sampler/PCPU-PS3-PROTOCOL.md).

The numerical observations come from the [ABI 3 result](../experiments/aurora-apsc-observer/ABI3-E-TICKET-RESULT.md), [PCPM packet](../experiments/linux-pcpm-sampler/native-evidence/mmio-abi2/README.md), [PS3 protocol](../experiments/linux-pcpm-sampler/PCPU-PS3-PROTOCOL.md), and [timestamp feasibility audit](../experiments/aurora-apsc-observer/LAST-CHG-TIME-CALIBRATION-FEASIBILITY.md). Register names and a decoded field layout do not fill the missing-fact column.

Reuse unchanged source, object, packaging and installation proofs by their hashes. Automate each boot's release/Build-ID/configuration, DT/firmware, topology, instrument dormancy and environmental checks into one report. New kernels still need device qualification; repetitive visual checks on an already qualified unchanged boot do not add idle-state evidence. A future rearm design must require a sealed/exported previous packet, validate dormancy, enforce per-session and cumulative budgets, and lock further acquisition after a read error or ambiguous control write. It cannot substitute for a fresh boot when carry-over prevents a valid comparison.

## Where m1n1 helps

A second host and USB cable can support faster kernel loading, remote collection and crash diagnosis. Asahi documents both direct Linux boot and hypervisor guest boot; they are distinct routes. For repeatable boot development, qualify the exact host/target revisions, board DTB, initramfs and native boot environment instead of repeatedly installing EFI images. This is an optional future infrastructure task, not a prerequisite for the staged #6 boot. [Tethered boot guide](https://github.com/AsahiLinux/docs/blob/626e62370b5af619cc4aec6f1eb8da11aca7a60d/docs/sw/tethered-boot.md), [direct loader](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/tools/linux.py).

Use EL2/hypervisor tracing to discover guest register accesses, PCs and control flow. Use native execution to validate the idle mechanism. The audited hypervisor permits retention-compatible deep WFI but suppresses some CYC_OVRD requests, skips ACC writes, substitutes guest shutdown and modifies CPU-state readback. It also generates timer activity and preserves USB/UART power dependencies. Therefore a guest-visible state is not an independent check of the shutdown that the hypervisor emulates. Async MMIO tracing still emulates accesses through stage-2 faults; it is not passive bus observation. [Power-register handling](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv_exc.c#L324-L338), [suppressed writes](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hv/__init__.py#L661-L703), [CPU-state substitution and timers](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv.c#L38-L168), [transport hooks](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hv/__init__.py#L1474-L1525), [access emulation](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv_vm.c#L996-L1083).

Asahi's currently published hypervisor targets are macOS 13.5 and 14.8.3; this does not qualify the previously inspected macOS 27 binary. Its guide requires matching m1n1 target/proxy builds because the ABI is unstable. Installing an older guest or enabling a recovery proxy would be a separately planned task with its own identities and boot-policy changes. [Pinned hypervisor guide](https://github.com/AsahiLinux/docs/blob/626e62370b5af619cc4aec6f1eb8da11aca7a60d/docs/sw/m1n1-hypervisor.md).

## What an independent observation must establish

For #6, first establish reproducible PCPU codes under controlled native workloads; rotate the active logical core to test slot identity, restore activity to test reversibility, and compare records-only/no-collector/MMIO blocks to measure the observer effect. Association with a named core's software idle interval additionally requires a qualified shared ordering method or counter bound. All are requirements of the [confirmation protocol](../experiments/linux-pcpm-sampler/PCPU-PS3-PROTOCOL.md); coarse workload labels alone cannot provide them.

Physical rail-off needs an independently characterized hardware indicator whose scope and retention behavior are known, or direct rail measurement synchronized with the experiment. Neither route is presently qualified here. An external whole-machine energy measurement can test consequences, but it must retain sampling bandwidth, integration window, supply/battery behavior, delivered work and uncertainty; it cannot identify the CPU rail by itself. These are proposed measurement requirements, not claims that a suitable device or rail access has been established. An independently qualified timing signal would be needed before reopening #5 timing work.

Measure progress as hypotheses resolved and calibrated observables gained. The immediate next result is the bounded #6 access qualification, followed by either a declared negative screen or a candidate that earns its separate confirmation experiment.

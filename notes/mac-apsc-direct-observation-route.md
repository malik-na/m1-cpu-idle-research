# Direct observation route for the last-core APSC wait

**Wayfinder context:** [Find a direct observation route for macOS’s last-core APSC wait](https://github.com/malik-na/m1-cpu-idle-research/issues/2). This note resolves an observation-method question; it reports no new BUSY sample or CPU power measurement.

**Target and evidence tier:** MacBookAir10,1 / J313 / T8103, native macOS 27.0 build 26A428, XNU `13432.1.9~1`, running kernel UUID `1F15A5DA-11D6-39EE-88D2-153E2F90F066`. The matching kernelcache SHA-256 is `e5e3b35cca34477d287a447bd1aa7a84f02f8543287b8db2eef722710e95a349`. The local instruction addresses below are *unslid*; a live observer must establish the guest or host slide. These identities and the disassembly are preserved in [the exact-build audit](mac-pmgr-command-order.md) and [running-kernel record](raw/driver-running-kernel-identity.txt). A read-only check during this research again returned macOS `27.0` / `26A428`, `RELEASE_ARM64_T8103`, and System Integrity Protection enabled. The original route-selection note used no root command. The follow-up below adds an operator-authenticated probe inventory; it involved no reboot, security-policy change, debugger attach, or enabled probe.

## Decision

The privileged FBT gate has now **failed on the running SIP-enabled 26A428 build**. On 2026-10-01, the operator authenticated in a terminal and ran `sudo -n /usr/sbin/dtrace -l -P fbt` through the [inventory collector](../tools/macos_fbt_inventory.py). DTrace returned **exit status 0**, but stdout contained only the column header and stderr said `failed to match fbt:::: System Integrity Protection is on`. The [sanitized full inventory result](raw/mac-fbt-inventory-26A428.json) preserves that contradiction, the lack of timeout, and zero probe rows. No probes were enabled. This is a failed availability gate, not a successful trace or proof that the named functions do not exist. More general root permission does not resolve the reported SIP restriction.

Consequently, there is **no demonstrated direct, non-reboot observer on this running build**. The saved `ktrace` reports PMGR callback brackets, not an internal call or APSC register value. Do not attempt a native FBT capture from this result. A changed target or security configuration would require a new inventory, followed by qualification of `cpuComplexIdleEnter`, `_waitAPSCPending`, and a return-value probe on `readACCReg` or its `readReg64` tail target. Apple's [SIP runtime guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/System_Integrity_Protection_Guide/RuntimeProtections/RuntimeProtections.html) provides context; the local inventory supplies the exact-build evidence.

For a **direct control-flow and sampled-BUSY observation on a clearly identified guest build**, the concrete route is a narrowly instrumented [m1n1 hypervisor](https://asahilinux.org/docs/sw/m1n1-hypervisor/) session. Its current guide qualifies macOS **13.5** and **14.8.3**, not this installed macOS 27 build. Preparing a separate supported macOS volume and booting m1n1 is a later, rebooting experiment with per-volume boot-policy changes; it is not part of this research session. A successful 14.8.3 trace would establish behavior of that guest binary under m1n1, **not** execution of the installed 26A428 path. An exact-build macOS 27 guest attempt needs its own boot-compatibility qualification before any trace can be interpreted. The guide explicitly warns that Apple does not promise ABI compatibility across versions and recommends a separate macOS copy rather than overriding the main installation.

## Why the available signals are insufficient

For the inventory gate, run the repository's [inventory collector](../tools/macos_fbt_inventory.py) from a terminal on the Mac:

```sh
python3 tools/macos_fbt_inventory.py --authenticate --output /tmp/m1-fbt-inventory
```

Use a fresh output directory. The collector authenticates through `sudo` in that terminal, then runs only `dtrace -l -P fbt`, with a 30-second inventory timeout. It does not enable probes. For the DTrace invocation it retains stdout, stderr, exit status, and timeout status locally; failed interactive authentication stops before that capture. A header-only or diagnostic-failed listing is marked unusable even if DTrace itself returns zero; review the raw listing before publication. A `sudo: a password is required` result means authentication failed before DTrace ran and says nothing about probe availability. Authentication in another terminal does not by itself demonstrate that the collector can use the same sudo credential cache. A successful listing still needs the symbol and returned-value qualification described above before any tracing experiment.

## The minimum direct event

The [matching disassembly](raw/driver-t8103-apsc-idle.disasm) gives the specific boundary. `cpuComplexIdleEnter` tests the skip flag at `this+0x73a52` and calls `_waitAPSCPending` at `9e99248` when bit 0 is clear. The [configuration audit](local-driver-skipflag-followup.md) predicts that flag clear from the captured `cpu-tvm` feature default; it is still not a runtime branch observation. `_waitAPSCPending` calls `readACCReg` for selector `0xE20020`; its CPU-domain loops repeat on **bit 31** and each loop ends with a clear read. The E/P physical command-register addresses resolved by [the register map audit](local-driver-notes.md) are `0x210e20020` and `0x211e20020`. [The exact-build command audit](mac-pmgr-command-order.md) also shows other calls to `_waitAPSCPending`, so **a read by that function alone is not proof of the last-core caller**.

Accept a direct observation only when one bounded record stream identifies all of these in the **same guest or host call context**:

1. The actual last-core dispatch into `cpuComplexIdleEnter`, the tested skip bit, CPU/cluster, and the executed call at `9e99248` (or equivalent instruction in a different guest build).
2. The subsequent `readACCReg`/`readReg64` access to the matching E or P command register, preserving the **raw returned value**, bit 31, access width, and whether the read was forwarded to hardware or emulated.
3. The completion of both wait loops or an explicit incomplete/dropped record, plus the command-write provenance when claiming overlap with a new DVFS request.

The stock m1n1 MMIO event carries `flags`, `pc`, `addr`, and `data`, **but no call stack or target timestamp** ([event structure](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv.h#L20-L26)). In this exact disassembly, `readACCReg` tail-branches to `readReg64`, whose `ldr` at `9b01b4c` performs the mapped read ([register-access excerpt](raw/driver-apsc-register-access.disasm)). Thus the MMIO event PC is at a **shared read helper**, not the `_waitAPSCPending` call site. Address plus PC alone still cannot prove the caller. A low-level guest extension could record the guest frame-pointer/return-address chain at that trap. After validated PAC and slide handling, `readReg64`'s saved return address should target the instruction after the wait's command-register `readACCReg` call (`9e9876c` or `9e987bc`), and the wait frame's saved return address should target `9e9924c` in `cpuComplexIdleEnter`. Those two addresses establish an intended helper/caller chain, **not** the last-core predicate. To label the event last-core, also validate `_cpuIdle`'s virtual call at `9b19e64` (continuation `9b19e68`) together with its one-to-zero active-count/transition branch, or collect an equivalent verified call-boundary record ([dispatch excerpt](raw/review-last-core-dispatch.disasm), [count analysis](local-driver-notes.md)). At the trapped load, saved return addresses are **intended continuations, not completed returns**; separate exit records are required to claim the wait loops or function finished. The exact binary's tail branch and frame-save instructions make this a **testable attribution design**, not a proven live unwind. Validate it against a sparse debugger breakpoint or other known call first; reject records with an invalid chain. An alternative is explicit call-site entry/exit records correlated to the MMIO read on the same guest CPU, with loss accounting. Both options require implementation review; stock MMIO logging alone is insufficient. These addresses apply **only to 26A428**: rederive every call and return PC from the exact guest image if using a supported older build.

The m1n1 source maps `ASYNC` traces through software stage-2 mappings, not passive bus snooping ([mapping selection](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hv/__init__.py#L323-L348)). Its C handler performs a mapped read **before** emitting a read event and emits a write event **before** attempting the write ([access order](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv_vm.c#L996-L1083)). A read value is therefore a value returned in that *trapped guest run*; a write event alone is only an attempted write. Trap time can let BUSY clear and can alter which core becomes last. Keep the trace narrow, buffer fixed records on target, avoid a host Python round trip for every poll, retain drop counts, and compare no optional trace, call-boundary-only, and narrow MMIO-trace conditions. The detailed [hypervisor validity audit](trace-validity.md) documents its timer/proxy activity, [ACC-write suppression](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/proxyclient/m1n1/hv/__init__.py#L661-L703), CPU-start substitution, and [shutdown emulation](https://github.com/AsahiLinux/m1n1/blob/3e354a2467f4f724f254362626cae0633918e0c1/src/hv/hv_exc.c#L324-L338). Those effects disqualify a guest run as a native idle-residency or energy measurement.

## Falsifiers and fallback

- A reliable call-site record that repeatedly takes the skip branch during qualifying last-core callbacks would refute the prediction that this guest configuration uses the wait. A reliable call record with only clear bit-31 reads would confirm the call but weaken the claim that pending commands are common **under those workloads**. Neither result is a physical-power result.
- A `0x27003010/30` marker, a long callback, or a trapped read without validated caller provenance is **inconclusive** for this question. Missing records, a guest that never reaches the candidate last-core condition, or a tracer that materially changes the active-core distribution also make a negative result inconclusive.
- The SIP/FBT inventory has failed. Unless macOS 27 can be qualified as an m1n1 guest or another direct route is demonstrated, the 26A428 **APSC wait/BUSY behavior remains exact-build static evidence only**. The existing native `ktrace` remains runtime software evidence for PMGR callback work, but it does not observe that wait or bit. A supported 14.8.3 guest can test the analogous mechanism with its *own* hash and disassembly. Decide whether Linux needs a change from a separate observation-only **native Linux** DVFS-write/BUSY/deep-WFI capture and later matched wake/energy measurements, as scoped in [the experiment backlog](../wiki/Experiment-Backlog.md). Even a positive guest BUSY read does not by itself justify a Linux wait.

This recommendation is a route to a falsifiable observation, not a claim that Asahi Linux or Aurora Silicon has missed a known hardware behavior. The inspected [Asahi/Aurora baseline](../wiki/Linux-and-Aurora-Baseline.md) and [Omacom audit](omacom-linux-source-audit.md) establish the Linux comparison scope; [the m1n1 validity audit](trace-validity.md) compares the pinned Asahi and Aurora hypervisor source used here.

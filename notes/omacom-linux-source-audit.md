# `omacom/linux`: base-M1 CPU-idle source audit

Research date: 2026-10-01 (Asia/Kolkata). Target of the wider project: MacBook Air J313 / T8103. This is a **public-source comparison**, not a probe of the Linux image installed on that Mac, a boot test, or a measurement of CPU power state. The question is whether the requested [`omacom/linux`](https://github.com/omacom/linux) repository changes the already checked M1 idle and DVFS baseline or the proposed APSC experiment.

## Result

The repository's default `asahi` branch resolved to **the same commit object** as `AsahiLinux/linux` `asahi`: `77cb8f24c2381a8abb7272d7bbdec548d6426a8a`. At the inspected `omacom` `aurora-wip` head, the M1 cpuidle, Apple cpufreq, T8103 DTS, generic PMGR domain driver, and T8103 PMGR include have the same Git blob IDs as `omacom`'s default branch. The `tb` branch retains the same cpuidle, cpufreq, and generic PMGR source but already includes Aurora Silicon's T8103 DTS and PMGR include. These are **file-level** observations, not equivalence of whole kernel trees or of built configurations. [Repository metadata](https://github.com/omacom/linux), [default tree](https://github.com/omacom/linux/tree/77cb8f24c2381a8abb7272d7bbdec548d6426a8a), [`aurora-wip` tree](https://github.com/omacom/linux/tree/4ec597a7427da2cf03c899406b7997c875d4a9fb), [`tb` tree](https://github.com/omacom/linux/tree/38c14f6107dfdb3366dee3cdfc3226cf4cda9ca2), [Asahi tree at the same commit](https://github.com/AsahiLinux/linux/tree/77cb8f24c2381a8abb7272d7bbdec548d6426a8a).

The inspected `omacom` CPU-control files do not supply a new M1 last-core APSC wait: the [cpuidle path](https://github.com/omacom/linux/blob/4ec597a7427da2cf03c899406b7997c875d4a9fb/drivers/cpuidle/cpuidle-apple.c#L21-L94) enters returning deep WFI without reading the cluster DVFS command, while the [cpufreq path](https://github.com/omacom/linux/blob/4ec597a7427da2cf03c899406b7997c875d4a9fb/drivers/cpufreq/apple-soc-cpufreq.c#L171-L207) polls command BUSY before issuing a new request and returns after the write. This is the same **source-permitted ordering** described in [the concurrency review](linux-dvfs-idle-concurrency.md). It does not establish that BUSY is set when native Linux reaches WFI, that such an overlap harms power or correctness, or that macOS's conditional wait should be transplanted.

## What the differences mean for this question

- The common [cpuidle driver](https://github.com/omacom/linux/blob/4ec597a7427da2cf03c899406b7997c875d4a9fb/drivers/cpuidle/cpuidle-apple.c#L21-L120) declares `WFI` and `CPU PD`; the latter saves state through CPU PM, selects deep WFI and returns after an interrupt. Its declared 10 microsecond exit latency and 10,000 microsecond target residency are policy metadata, not hardware measurements. There is no APSC command-register read in that driver.
- `omacom`'s [Apple cpufreq driver](https://github.com/omacom/linux/blob/4ec597a7427da2cf03c899406b7997c875d4a9fb/drivers/cpufreq/apple-soc-cpufreq.c#L171-L207) tests DVFS command `BUSY` at bit 31 **before** `writeq_relaxed()` and does not wait for that write's completion. It marks fast switching possible and permits DVFS from any CPU. These source choices leave the candidate idle/DVFS timeline open; they do not prove that it occurs. [Policy setup](https://github.com/omacom/linux/blob/4ec597a7427da2cf03c899406b7997c875d4a9fb/drivers/cpufreq/apple-soc-cpufreq.c#L304-L317).
- Aurora Silicon's different cpufreq blob adds a post-write `verify_transition` poll, but [that flag is set in the T8140 descriptor](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/drivers/cpufreq/apple-soc-cpufreq.c#L95-L122), not in `soc_t8103_info`; the [post-write poll is conditional on the flag](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/drivers/cpufreq/apple-soc-cpufreq.c#L239-L258). It therefore does not establish a completed DVFS request before base-M1 idle entry. This says nothing about all other effects of Aurora's cpufreq changes.
- Aurora Silicon's generic PMGR domain source masks [`APPLE_PMGR_BUSY` bit 11](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/drivers/pmdomain/apple/pmgr-pwrstate.c#L25-L30) from whole-word domain writes and rate-limits selected diagnostics [in the changed power-state path](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/drivers/pmdomain/apple/pmgr-pwrstate.c#L65-L104). This is **not** the Apple cluster DVFS command `BUSY` bit 31. Conflating the two would manufacture a CPU-idle fix that the source does not contain.
- Aurora Silicon's T8103 DTS adds CIO/ACIO, USB4 and related PCIe device nodes relative to the `omacom` default DTS; `omacom` `tb` has that same DTS blob. Aurora's T8103 PMGR include adds `apple,always-on` to the [`ps_atc0_pcie`](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/arch/arm64/boot/dts/apple/t8103-pmgr.dtsi#L861-L869) and [`ps_atc1_pcie`](https://github.com/aurora-silicon/linux/blob/1d2904fd3301c63620f07c81ae79f2486a81a9a6/arch/arm64/boot/dts/apple/t8103-pmgr.dtsi#L906-L914) domains; `omacom` `tb` has the identical include. These are relevant **whole-system power confounders** when comparing kernels, even though the common CPU-idle driver is unchanged. That confound is an inference from the source, not a measured wattage effect.

## Boundary and next experiment

The audit inspected selected files, branch heads and repository metadata. It did not check every branch's complete tree, compare build configurations, verify the actually booted Linux kernel or boot firmware, or run a native experiment. A branch head or source blob cannot establish the installed driver, governor, fast-switch state, clock/power-domain residency, or energy on the target. Follow [Evidence Standard](../wiki/Evidence-Standard.md) before raising the claim level.

For [experiment E2](../wiki/Experiment-Backlog.md), first identify the native Linux kernel/DT/m1n1 build, then capture a bounded, observation-only timeline of DVFS submissions and deep-WFI entry with command BUSY samples, writer CPU, target cluster, timestamps and loss accounting. If `tb` or another device-tree variant is used for comparison, record peripheral-domain differences and external USB conditions separately from CPU idle. A BUSY sample near WFI would support the candidate ordering; a negative, sufficiently sensitive run would weaken it. Neither outcome alone proves a power benefit from copying macOS's conditional APSC wait. [Detailed instrumentation proposal](linux-dvfs-idle-concurrency.md), [macOS control path](../wiki/MacOS-Control-Path.md).
